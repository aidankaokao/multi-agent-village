# Roadmap — 由簡到繁

每個階段都是「能跑、能看、能展示」的完整切片。架構細節見 [ARCHITECTURE.md](ARCHITECTURE.md)。

## Phase 0 — 地基 ✅

- [x] `backend/`：uv 專案、FastAPI、`/health`
- [x] SQLite + SQLAlchemy；`.gitignore` 排除 DB、`.env`、金鑰檔
- [x] `security/crypto.py`：主金鑰載入（環境變數 / 專案外金鑰檔）、AES-256-GCM 加解密，附單元測試
- [x] LLM 註冊 API：provider 增刪改、測試連線、列出 / 註冊模型、模型分級；API key 只寫不讀
- [x] `LLMProvider`：OpenAI 相容 client，`chat()` 與 `chat_json(schema)`，從 DB 載入設定
- [x] 前端「LLM 設定」頁：註冊本地 Ollama 與一個雲端 provider，並指派 `large` / `small`
- [x] `frontend/`：Vite + React + Phaser，畫出一塊草地，5 個角色用 `assets/sprites` 隨機閒晃（四向走路動畫）
- [x] WebSocket 連通，後端送假事件 → 指定角色頭頂出現 working 泡泡

**驗收**：打開網頁看到村民在走；按一個 debug 按鈕，詩人頭上冒泡泡；在設定頁註冊 Ollama 和雲端模型後都能測試成功；直接打開 SQLite 只看得到密文。

## Phase 1 — MVP：詩人 × 笑話師合作 ✅

目標題目：**「寫一首關於貓的詩，然後把它改成笑話」**

- [x] `AgentSpec`（card + x-village + prompt + validate）/ `AgentRegistry`
- [x] `agents/poet/agent.yaml`、`agents/jester/agent.yaml`
- [x] 村長：`@指名` → LLM 規劃（JSON schema + 帶錯誤回饋重試）→ 剪掉沒被要求的步驟 → 關鍵字備援 → 直接回覆
- [x] Executor：依序執行、`use` 指定的成果組成 `{context}`、發事件、交接動畫
- [x] 聊天面板：送出問題、即時步驟狀態、最終答案、可展開執行過程（模型、耗時、輸出、警告）
- [x] 村落動畫：由真實事件驅動；村民清單來自 `/api/agents`，新增 agent 會淡入登場
- [x] Harness 最小版：清 `<think>`、非空 / 長度檢查、中英髒話詞表；不合格帶回饋重試一次，仍不合格則遮蔽 / 標警告
- [x] 模型分級互為備援：small 沒設定或失敗時用 large

實測（Ollama qwen3.5:9b、思考 none，只設定 large）：「貓詩 → 笑話」約 20 秒完成；`@指名` 不經 LLM 立即開始。

已知限制（留待後續）：
- 本地模型偶爾混入簡體字 → 可在 harness 加 OpenCC 繁簡轉換
- 步驟目前依序執行；平行步驟在 Phase 3

**驗收**：
1. 單一任務「講個笑話」→ 只有笑話師動
2. 組合任務「寫詩再變笑話」→ 兩位依序動，結果正確串接
3. 把模型換成本地小模型，同樣兩題至少能靠退路完成

**建議測試題**：
- 寫一首關於颱風天的詩，再把它改編成冷笑話
- 講一個工程師的笑話
- @poet 寫一首五言絕句 → @jester

## Phase 2 — 在介面上建立村民（英文翻譯）✅

使用者的角色是「介面使用者」：新增村民的所有功能都在前端完成，不用碰檔案或後端。

**A. 村民管理介面（已完成）**

- [x] 村民改存 DB（`agents` 表）；`agents/*.yaml` 只是第一次啟動匯入的內建範例
- [x] 「村民」分頁：列表、新增、複製、編輯、停用 / 啟用、刪除、還原內建範例
- [x] 設定表單：名片（名稱、描述、技能與請求範例）、外觀、住處（點地圖）、關鍵字、模型與 temperature、system prompt、任務模板、自動檢查
- [x] 試打：用編輯中的草稿直接跑一次，可指定模型比較雲端 / 本地
- [x] 測試題：任務 + 期望條件（應包含 / 不應包含 / 語言 / 字數 / regex），一鍵全部執行看通過率與紀錄
- [x] 匯入 / 匯出 YAML
- [x] 存檔後村子即時更新（登場、換裝、改名、離開）

**B. 教學：使用者在介面上建立翻譯官（已完成）**

1. 「＋ 新增村民」，填名片：名稱、ID `translator`、描述、技能與請求範例
2. 選外觀（翻譯官）、點地圖選住處、填關鍵字
3. 模型選 small、temperature 調低（約 0.2）
4. 寫 system prompt：自動判斷中翻英 / 英翻中、只輸出譯文、保留格式
5. 「試打」幾次，把好的任務加入測試題，補上期望條件
6. 「測試題」全部執行，修改 prompt 後再跑，比較雲端與本地模型
7. 建立後在村子看到翻譯官，再到問答試三人接力：「寫一首關於海的詩，翻成英文，再改成笑話」

心得：「應包含」只適合一定會出現的詞（例如譯文裡的專有名詞）；創作類（寫月亮的詩不一定有 moon）用「不應包含」、語言、字數檢查即可。

## Phase 2.5 — 村民工坊：跟工匠聊天打造村民 ✅

使用者用日常的話描述想要的村民，工匠（系統角色，保留名稱 `craftsman`）追問、產生第一版設定，使用者再到編輯器微調後建立。

- [x] 追問：工匠判斷資訊夠不夠，用日常問題追問（不出現 prompt / temperature 等術語），一次最多 2 題，最多 4 輪
- [x] 打造：LLM 只填「藍圖」（名稱、描述、範例、關鍵字、外觀、穩定 / 創意、長短、工作守則、測試題），由程式組成 AgentSpec
- [x] 程式把關：ID 轉換與避免重複、外觀只能選現有角色、住處挑地圖空位、任務模板固定、「穩定 / 創意」「長短」換算成 temperature / 字數上限；測試題的「應包含」只留任務或素材裡就有的詞，「不應包含」去掉少於 3 字的短詞
- [x] 藍圖不合格帶錯誤重做（最多 2 次）；LLM 不能用時，追問改用固定問題、打造改用對話內容拼基本草稿
- [x] 打造後自動跑工匠出的測試題；可以繼續聊天要求修改（「語氣活潑一點」）再重新打造
- [x] 草稿不會自動儲存：「打開編輯器」確認後才建立；建立前可以「回工坊」繼續聊
- [x] 新角色外觀：學者、商人、農夫、廚師；工匠在村子右下角，工作時有動態（`workshop.*` 事件）
- [x] 修改已建立的村民：編輯器「🔨 請工匠幫忙改」→ 用聊天說哪裡要改 → 草稿（保留 id、住處、指定模型、原有測試題）→ 編輯器確認後儲存
- [x] 字數上限由程式寫進工作守則最後一條（`- 長度：…`），村民事先就知道上限；工匠被要求縮短時改用結構限制（幾點、每點幾字）
- [ ] 之後：依測試失敗原因建議修改

## Phase 3 — Harness 強化與審核員 ✅

- [x] 審核員（系統角色 `reviewer`，外觀 auditor）：最終答案送出前用 LLM 檢查「有沒有做到要求、有沒有違反明確要求、內容是否恰當」；
      只有明顯問題才退回，附理由與修改建議交給負責的村民重做（預設 1 次），之後照實交出並標示「審核有疑慮」；審核員不能用時略過不擋答案
- [x] 失敗回饋迴圈：harness 檢查不合格時帶錯誤訊息重做（Phase 1 已有），重做原因寫進紀錄
- [x] 每步逾時（預設 180 秒）、問答中按「■ 停止」取消（已完成的步驟保留）
- [x] 執行紀錄存 DB（`runs` 表）：計畫、每一步送出的完整訊息與輸出、重做原因、被退回的版本、審核結果、耗時、token；
      「紀錄」分頁可搜尋、查看、刪除；問答每則回答有「📜 紀錄」直接跳過去；伺服器重啟時沒跑完的標成 interrupted
- [x] 平行步驟：互不依賴的步驟同時執行（最多 N 個）；有多個最終步驟時回答合併顯示
- [x] 「村規」分頁（`settings` 表）：審核員開關 / 模型 / 重做次數、平行執行與上限、每步逾時、紀錄保留筆數

## Phase 4 — 工具型村民 ✅

使用者不寫程式：工具（可靠的程式碼）放在後端工具箱，使用者在介面上把村民設成「工具型」並挑一個工具。
LLM 只負責把請求整理成工具的參數（JSON schema），計算由程式完成，弱模型也不會算錯。

- [x] 工具箱（`backend/village/tools/`）：計算機（AST 白名單安全求值，不用 eval）、圖表（長條 / 折線 / 圓餅，產生 SVG）、日期（今天、相差幾天、加減天數）
- [x] 工具型村民的執行：LLM 整理參數 → 工具計算 → 參數不合法帶錯誤回饋重來（2 次）→ 仍不行改用工具的退路從文字直接抓參數（沒有 LLM 也能算簡單的題目）
- [x] 「說明」選項：算完請 LLM 用一句話說明，說明裡的數字和工具結果不一致就只給工具結果
- [x] 附件：工具產生的圖片顯示在問答、試打、紀錄裡，可以下載（`<img>` 顯示 SVG，文字都有跳脫）
- [x] 介面：村民編輯器選「對話型 / 工具型」、挑工具、參數整理說明（留空用工具預設）；試打與紀錄顯示交給工具的參數
- [x] 工匠也會打造工具型村民（藍圖多一個 tool 欄位）
- [x] 內建範例：計算機（calculator）、圖表師（chart）
- [x] 日期工具修正：年份一律由程式決定（日期可不寫年份、可寫節日名稱）；新增 until（自動抓下一次）；每次附上今天日期
- [x] 圖片點擊放大（彈窗，可切換上一張 / 下一張）
- [x] JSON 輸出被截斷時換下一個模型；「支援 JSON schema」取消勾選的模型改為不送約束照樣使用
- [ ] 之後：更多工具（單位換算、匯率、網頁查詢…）；多個工具給同一位村民

## Phase 5 — 帳號與長期記憶 ✅

**5A 帳號與資料庫遷移（已完成）**

- [x] Alembic migration（啟動時自動升級；舊 DB 先標記基準版本再升級，資料保留）；加入 asyncpg，切 Postgres 只改 `DATABASE_URL`
- [x] 帳號：第一位註冊者是管理員，之後註冊是一般成員；管理員可新增 / 改角色 / 停用 / 重設密碼 / 刪除，並可關閉公開註冊
- [x] 登入：httpOnly cookie session（記住 30 天、滑動延長），DB 只存 token 的 SHA-256；密碼 scrypt；連續失敗暫時鎖定
- [x] 權限：成員可以問答、看自己的紀錄；管理員管理村民、村規、LLM 設定、帳號。取代原本的 admin token
- [x] 隱私：別人的問答事件只送村落動畫需要的欄位（大家看得到村民在動，看不到內容）；執行紀錄依帳號分開
- [x] 登入頁：示範村落（劇本驅動的假事件 + 字幕）展示平台特色，登入 / 註冊 / 第一次建立管理員
- [x] CLI：`village reset-password <帳號>`、`village create-admin <帳號>`
- [x] 刪除帳號：管理員刪除其他人（帳號列表直接有刪除鈕）；本人輸入密碼刪除自己（唯一的管理員不能刪自己）
- [x] LLM 設定屬於各個帳號：自己的供應商、API key、模型與 large / small 分級，自己的額度；沒設定時提醒並擋下問答
      （migration 0003 清除了原本沒有擁有者的 LLM 設定）。之後可加「全局預設的本地 LLM」給沒設定的人用

**5B 對話與多輪上下文（已完成）**

- [x] 對話（`conversations`、`messages`）存 DB，與執行紀錄分開（不受紀錄保留筆數影響）；重新整理後接回最近的對話
- [x] 問答視窗的對話列表：切換、改名、刪除；「＋ 新對話」真的開新對話
- [x] 多輪上下文：村長規劃看得到前幾輪，接續的請求在 `use` 填 `"prev"`（上一輪的回答）交給村民；
      @指名與關鍵字備援遇到「它、這個、剛剛、上面、再…」也自動帶入；村長直接回覆與審核員也看得到前文
- [x] 村規「問答時帶入前幾輪對話」（預設 3，0 = 關閉）

**5C 長期記憶（已完成）**

- [x] 書記（系統角色 `scribe`）：問答後在背景從使用者的話萃取「關於本人、長期有效」的事實 / 偏好存 `memories`（migration 0005），
      也處理「忘記…」；句子沒提到自己就不呼叫 LLM；用 small 分級；LLM 不能用時退回固定句型；去除重複
- [x] 問答前挑相關記憶（不多就全部；多時偏好類必帶、其餘依字詞重疊度）帶進每位村民的參考資料與村長直接回覆，跨對話有效
- [x] 「記憶」頁（每個人都有）：查看、修改、停用、刪除、手動新增、全部清除；回答下方顯示「書記記下 / 忘掉」
- [x] 村規：問答時帶入記憶、書記自動記錄、每次最多帶入幾條
- [ ] 之後：記憶多了以後改用向量檢索（Postgres + pgvector）

## Phase 5V — 視覺模型：鑑定師看圖

決定：做成系統角色「鑑定師」（不讓村長派工）；追問時重看原圖；圖片跟著對話保存。
視覺模型自成 `vision` 分級，不和 large / small 互相備援，一般問答不會用到。

- [x] A：訊息可以帶圖片（OpenAI 相容 / OpenRouter / Ollama 的 image_url、Anthropic 的 image block）；
      `vision` 分級；看圖測驗（當場畫四位數字＋彩色圖形，兩個都答對才算通過，通過才能放進 vision 分級）
- [x] B：💬 附圖上傳（🖼️ 按鈕 / 貼上 / 拖曳）、前端縮圖（長邊 1568px）並重新編碼成 JPEG（去掉 EXIF）、
      `chat_images` 表（只有本人看得到，跟著對話刪除）、沒有視覺模型時附圖按鈕變灰、村規「每次最多附幾張圖」
- [x] C：鑑定師角色（`core/appraiser.py`）：依問題把圖轉成文字交給村長、村民、審核員；追問時重看原圖；
      看不了圖時老實說；村長 LLM 不能用時直接交出鑑定內容；動畫、事件、執行紀錄

## Phase 6G — 生圖：畫家村民

決定：畫家做成村民（村長派工，可以和詩人、鑑定師串接），不是系統角色；先做純文字生圖，修圖（以附圖為底）之後再說；
先接 OpenRouter 的生圖 API（`POST /images`）；每次問答最多 1 張、每人每天 20 張；畫作保存 14 天後自動清掉（不開放設定）。

- [x] A：生圖模型（`llm_models.output=image`，從供應商「🎨 列出生圖模型」註冊）、`image` 分級（不和其他分級混用，
      生圖模型也不能拿來對話）、生圖測驗（畫紅蘋果，拿到點陣圖就通過，有視覺模型時請鑑定師看一眼）、
      畫作存 `chat_images`（kind=generated、expires_at 14 天、啟動時與每 6 小時清理過期的；SVG 不收）
- [x] B：畫家村民（工具 `painter`：small 分級整理英文提示詞 → image 分級畫圖；整理失敗用原話畫）、
      回答裡顯示畫作（放大 / 下載 / 過期提示）、村規上限（`paint_per_run` 每次 1 張、`paint_per_day` 每人 24 小時 20 張）、
      審核員退件不重畫（工具 `costly`）、角色 sprite
- [x] 實測修正：村長規劃不再誤刪「原話要求」的步驟（例如「畫一隻狗，再畫一隻兔子」）；
      重複的畫家步驟（把鑑定結果又畫一次）會被移除；名冊註明畫家每次都要花錢
- [ ] 之後：修圖（附圖當參考圖，`input_references`）
- [ ] 之後：本機生圖。評估過 Ollama（x/flux2-klein:4b）：2026/10 的版本不支援生圖模型（API 與 CLI 都拒絕），
      使用者決定先只用 OpenRouter；Ollama 恢復支援、或改接 ComfyUI / Draw Things 這類有 HTTP API 的工具時再做

## Phase 7+ — 之後的想像

- Postgres + TimescaleDB（事件與指標）、pgvector（記憶與 card 檢索）
- Agent 之間直接對話（不經村長），例如詩人主動請翻譯官幫忙
- 市集頁面：瀏覽 / 啟用 / 停用 / 匯入外部 A2A agent
- 村落養成：常被叫用的村民升級、房子變大；任務看板
- 多使用者同時在村裡看得到彼此的任務
